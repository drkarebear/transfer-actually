Accessibility is part of the build

Accessibility

Transfer information is already complicated. The interface should not add unnecessary barriers.

Design target

Transfer, Actually is designed toward WCAG 2.2 AA practices, including keyboard access, visible focus, readable contrast, responsive reflow, labeled controls, large targets, reduced-motion support, and information that does not depend on color alone.

What this statement does not claim

This is not a formal accessibility certification. Automated and rendered checks can catch many problems, but assistive-technology and human testing remain important.

Current accessibility practices

  • Semantic headings, landmarks, fieldsets, legends, and labels are used for page structure and interactive choices.
  • Visible radio buttons and checkboxes are consistently sized and keyboard accessible.
  • Interactive feedback is exposed through accessible live regions where appropriate.
  • Focus indicators remain visible on light and dark surfaces.
  • Pages reflow at narrow phone widths without requiring horizontal page scrolling.
  • Reduced-motion preferences are respected.
  • Decorative symbols are not used as the only way to communicate meaning.
  • System fonts and local assets avoid unnecessary third-party dependencies.

If something is difficult to use

Accessibility is an ongoing maintenance task, especially as transfer tools and pages are added. If a page or control is difficult to use with a keyboard, screen reader, magnification, voice input, high-contrast mode, or another access method, the problem should be corrected in the source rather than worked around with a separate inaccessible version.

Privacy and accessibility support each other here: the site intentionally avoids third-party embeds, trackers, and complex account interfaces, which reduces both privacy exposure and accessibility failure points.
